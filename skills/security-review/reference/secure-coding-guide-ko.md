## 1. 공통 보안 코딩 원칙 (제3장 — 7개)

1. 신뢰 경계 밖의 **모든** 입력은 악의적이라고 전제하고 검증한다.
2. 보안 통제는 **서버 측에서 강제**하고 기본값은 **거부(deny by default)**.
3. 최소 권한 · 직무 분리 · 안전한 기본 설정.
4. 비밀번호·키·토큰·개인정보를 **코드·로그·오류화면**에 노출하지 않는다.
5. 검증된 표준 라이브러리와 프레임워크 기능을 우선 사용하고 **임의 구현을 최소화**한다.
6. 오류 메시지는 필요한 범위로 제한하고 진단정보는 접근 통제된 로그로 분리한다. 외부 입력을 로그에 쓸 때 **개행(`\r`,`\n`)·제어문자를 제거·인코딩**한다.
7. 보안 통제 **우회 가능성**을 전제로 단위·통합·침투 관점 시험을 수행한다.

## 2. 조항별 코딩 기준 (제4장 제5~16조)

각 항목은 **[사내 기준] → [코드에서 확인할 것]** 순이다. 취약/안전 예시는 원문 그대로다.

### 제5조 — 입력값 검증 및 인코딩
- 모든 외부 입력에 **형식·길이·범위·문자집합·허용목록**을 **서버에서** 검증. **차단목록만으로 검증하지 않는다.**
- 출력 시 **출력 위치별 인코딩**(HTML 본문 / 속성 / JavaScript / URL)을 구분해 적용.
- 확인 대상은 요청 파라미터뿐 아니라 **헤더·쿠키·파일명·외부 API 응답·메시지 큐 입력**까지.

### 제6조 — SQL/NoSQL 및 ORM 주입 방지
- 사용자 입력을 SQL·NoSQL·검색식에 **문자열 결합 금지**. Prepared Statement / 파라미터 바인딩 / ORM 안전 조회 API 사용.
- **동적 식별자(테이블·컬럼·정렬키)는 허용목록에서 선택**한다. (바인딩으로 못 막는 지점 — 리뷰에서 가장 자주 놓침)
```python
# 취약
sql = 'SELECT * FROM users WHERE id = ' + user_id
# 안전
cursor.execute('SELECT * FROM users WHERE id = %s', (user_id,))
```

### 제7조 — 명령어·코드 실행 방지
- OS 명령·셸·**eval류 기능 사용 금지**. 불가피하면 명령·인자를 **고정**하고 **셸 호출 없이 배열 인자**로 전달 + 허용목록 검증 + 최소 권한 계정.
- `subprocess` / `child_process` / `eval` / `Function` / 템플릿 동적 실행 사용처는 **전수** 확인.
```python
# 취약
subprocess.run('grep ' + keyword, shell=True)
# 안전
subprocess.run(['grep', '--', keyword, '/srv/app/data'], check=True)
```

### 제8조 — XSS 및 콘텐츠 삽입 방지
- 사용자 데이터를 HTML로 직접 삽입 금지. **템플릿 자동 이스케이프를 유지**하고, HTML 허용이 필요하면 검증된 정화(sanitization) 정책 적용. **CSP 권장.**
- `innerHTML` / `dangerouslySetInnerHTML` / 템플릿 raw 출력 / **URL 스킴 검증**(`javascript:` 차단) 확인.
```js
// 취약
element.innerHTML = userInput;
// 안전
element.textContent = userInput;
```

### 제9조 — 경로 조작 및 파일 처리
- 파일명·경로를 신뢰하지 않는다. **저장 파일명은 서버에서 새로 부여**한다.
- 기준 디렉터리를 **정규화한 뒤 하위 경로 여부를 확인**한다.
- 업로드는 **확장자·MIME·파일 시그니처·크기·개수**를 검증하고 **웹 루트 밖**에 저장한다.
- 확인: `../` 포함 경로, **압축 해제 경로(zip slip)**, 다운로드 권한, 업로드 파일 검사·격리.

### 제10조 — 인증·인가
- 인증 상태와 **대상 자원에 대한 권한을 매 요청마다 서버에서** 검증.
- **클라이언트가 보낸 역할·사용자 ID를 권한 판단 근거로 쓰지 않는다.**
- 관리 기능은 일반 기능과 분리하고 **MFA 등 강화 인증** 적용.
- 확인: **IDOR**, URL·**메서드별** 권한 체크, 관리자 API 접근통제 시험 결과.

### 제11조 — 세션 및 토큰 관리
- **인증 성공·권한 변경 시 세션 식별자 재발급**(세션 고정 방지).
- 쿠키에 **Secure · HttpOnly · SameSite** 적용.
- 토큰은 **짧은 만료 + 서명 검증 + audience(aud) + issuer(iss) 검증**.
- **로그아웃·비밀번호 변경 시 무효화 정책**을 둔다.

### 제12조 — 암호화 및 중요정보 보호
- 전송 구간 최신 TLS. **인증서 검증 우회 금지.**
- 비밀번호는 **적응형 단방향 해시(Argon2 / bcrypt / PBKDF2)** + **사용자별 고유 Salt 최소 16 bytes**.
  **복호화 가능한 암호화 방식으로 비밀번호를 저장하는 것은 금지.**
- 키·비밀값은 승인된 비밀관리 체계 또는 환경별 안전한 설정으로 관리.
- 확인: 소스·설정·**CI 로그**의 비밀값 노출, 취약 해시(MD5/SHA1)·취약 암호 알고리즘, TLS 검증 비활성화.

### 제13조 — 오류 처리 및 로그
- 사용자에게는 **일반화된 오류만**. 스택트레이스·쿼리·파일경로·토큰 노출 금지.
- 보안 이벤트는 **시간·주체·대상·행위·결과**를 기록하되 아래는 **마스킹하거나 기록 대상에서 제외**한다.
- 외부 입력 로그 기록 시 **개행·제어문자 제거·인코딩으로 로그 위조(Log Injection) 방지**. 로그의 **위변조·접근을 통제**한다.

| 항목 | 세부 |
|---|---|
| 인증 및 비밀값 | 비밀번호, API Key, Access/Refresh 토큰, 개인 암호화키 |
| 고유식별정보·금융정보 | 주민등록번호, 외국인등록번호, 여권번호, 운전면허번호, 계좌번호, 카드번호 |
| 개인정보 | 이메일 주소, 전화번호, 상세 주소 (필요 시 부분 마스킹) |

### 제14조 — 역직렬화 및 데이터 파서
- 신뢰할 수 없는 데이터를 **위험한 역직렬화 함수로 복원 금지**. JSON 등 단순 형식 우선 + **스키마 검증 + 크기 제한**.
- **XML은 외부 엔터티·DTD 처리 비활성화**(XXE).
- 확인: `pickle`, YAML unsafe load, XML 외부 엔터티, **객체 타입 자동 복원**.

### 제15조 — 외부 연동 및 SSRF
- 외부 URL·리다이렉트·**웹훅 수신 주소는 허용목록**으로 제한. **사설·로컬·클라우드 메타데이터 대역 차단**(예: `169.254.169.254`).
- **시간초과 · 응답 크기 · 리다이렉트 횟수** 제한.
- 확인: URL fetch 기능, 이미지·문서 변환 서비스, 웹훅 호출의 목적지 검증.

### 제16조 — 동시성·자원 관리
- 요청·파일·페이징·쿼리·연결에 **상한과 시간초과**.
- 중요 상태 변경은 **원자성·중복 요청 방지(멱등키)·경합 조건**을 고려.
- 확인: 대용량 입력, 반복 요청, 재시도, 타임아웃, **rate limit**, 중복처리 키.

## 3. 언어별 기준 (제5장)

### 제17조 — Python
1. `pickle`·`marshal` 등 신뢰불가 데이터 역직렬화 금지. PyYAML은 **안전한 로더**(`safe_load`) + 입력 스키마 검증.
2. `subprocess`는 **`shell=True` 금지**, 명령과 인자 분리. `os.system`·`eval`·`exec` **원칙적 금지**.
3. `requests` 등 HTTP 클라이언트에서 **인증서 검증 비활성화 금지**, **connect/read timeout 지정**.
4. 경로는 `pathlib` 등으로 **정규화**하고 기준 경로를 벗어나지 않는지 검증.
5. 의존성은 **고정 버전 + 신뢰 가능한 저장소**, 취약점 점검 결과를 **배포 전** 검토.

### 제18조 — JavaScript / TypeScript
1. `eval`·`new Function`·**문자열 기반 `setTimeout`/`setInterval`** 금지.
2. `innerHTML`·`outerHTML`·`insertAdjacentHTML` 사용 제한 → 텍스트 출력 API·프레임워크 기본 이스케이프 사용.
3. Node.js `child_process`는 **shell 옵션 미사용**, 사용자 입력을 명령 문자열로 결합 금지.
4. **프로토타입 오염 방지** — 외부 객체 병합·복사 시 위험 키(`__proto__`, `constructor`, `prototype`) 차단 + 스키마 검증.
5. npm은 **lock 파일 관리**, 설치 스크립트·의존성 취약점·무단 패키지 변경 검토.

## 4. 외부 라이브러리·오픈소스 (제6장)
1. 신규 라이브러리 도입 전 **기능 필요성·유지보수 상태·라이선스·알려진 취약점·공급망 위험** 검토.
2. **의존성 목록(SBOM 또는 준하는 목록)** 을 프로젝트별로 최신화(패키지명·버전·용도).
3. **고위험 또는 악용이 확인된 취약점은 배포 전 조치.** 곤란하면 예외승인(§6).
4. 개발·빌드 환경 설치는 **승인된 저장소 + 잠금 파일**. 비밀값 포함 패키지·산출물 공개 금지.

## 5. 심각도 등급과 조치 기한 (제20조) — **게이트 판정의 근거**

| 등급 | 기준 예시 | 조치 원칙 | security-review 판정 |
|---|---|---|---|
| **긴급** | 원격 코드 실행, 인증 우회, 대규모 중요정보 유출 가능성 | **배포 전 조치 원칙**, 운영 중 발견 시 즉시 완화 | **failed** |
| **높음** | 권한 상승, SQL 주입, 저장형 XSS 등 악용 영향이 큰 취약점 | 배포 전 조치 **또는 승인된 임시 통제** | **failed** (승인된 예외는 §6) |
| **보통** | 제한적 조건에서 악용 가능하거나 영향이 제한적 | 위험도·변경 일정에 따라 **기한을 정해** 조치 | passed 가능 — **팔로우업 원장에 기한과 함께 등재 필수** |
| **낮음** | 악용 난이도가 높고 영향이 경미 | 정기 개선계획 반영 | passed — 코멘트 |

- 중요도 판단은 **공격 가능성 · 노출 범위 · 정보 중요도 · 보완 통제 존재**를 함께 고려한다.
- 조치 후 **재시험 또는 코드리뷰로 조치의 유효성을 확인**한다(재리뷰 없이 닫지 않는다).
- 다음은 등급과 무관하게 항상 **긴급/높음**으로 취급한다: 비밀값 하드코딩, TLS 검증 비활성화, 비밀번호 평문·가역 암호화·취약 해시 저장, 민감정보 평문 로그, 인증/인가 누락.

## 6. 예외처리 (제9장)

가이드 충족이 곤란하면 **배포 전에** 개발책임자가 예외신청 → **정보보호부서 검토 + 승인권자 승인**. **영구 면제가 아니며 유효기간과 개선계획을 반드시 포함**한다.

| 필수 기재 | 내용 | 원장 필드 |
|---|---|---|
| 대상 및 사유 | 시스템·기능·**코드 위치**, 미준수 사유, 대안 검토 결과 | `target`, `reason` |
| 위험평가 | 악용 시나리오, 영향, 노출 범위, 잔여 위험 | `risk` |
| 보완통제 | WAF, 네트워크 제한, 모니터링, 기능 제한 등 임시 통제 | `compensating_controls` |
| 개선계획 | 조치 담당자, 완료 목표일, 검증 방법 | `remediation_plan` |
| 승인 | 개발책임자·정보보호부서·승인권자 + **유효기간** | `approved_by`, `expires_on` |

→ 원장 스키마와 훅 동작은 `../SKILL.md` §5 참조. **만료일이 지나면 훅이 자동으로 커밋을 다시 차단**한다.

## 7. 점검 원칙과 증적 (제19조 · 제21조)
- 개발·변경 완료 **전** 자체 점검 + 동료 코드리뷰. 정적 분석·의존성 점검·동적 점검을 위험도에 따라 조합.
- **오탐으로 처리할 때에도 판단 근거를 기록한다.** (제19조 3항 — 리뷰 로그에 "오탐 판정" 절 필수)
- 증적(보안 요구사항, 코드리뷰 기록, 점검 결과, 조치 결과, 예외승인서, 배포 승인 기록)은 프로젝트별 보관.
  **별도 기준이 없으면 최소 3년.** 증적에 중요정보가 들어가지 않도록 **마스킹하고 접근을 통제**한다.
- 다음 기능은 **코드리뷰와 자동화 점검을 반드시 수행**한다(제7장): 인터넷 공개 서비스, 개인정보 처리, 관리자 기능, 외부 연동, 중요정보 처리.

| 단계 | 필수 증적 | 이 스킬셋의 산출물 |
|---|---|---|

## 8. 별첨 1 — 시큐어코딩 점검 체크리스트 (20항목)

> `docs/02-design/security.md`와 `security-review-log.md`에 **이 20항목을 그대로 옮겨** 결과(적합/해당없음/개선필요)와 근거·조치계획을 채운다.

| 구분 | 점검 항목 | 조항 |
|---|---|---|
| 공통 | 외부 입력값에 대한 형식·길이·범위·허용목록 검증이 **서버 측에** 구현되었는가? | 제5조 |
| 공통 | 출력 위치에 맞는 인코딩 또는 템플릿 자동 이스케이프가 적용되었는가? | 제5조 |
| 주입 | SQL/NoSQL/검색식에 사용자 입력을 문자열 결합하지 않고 파라미터 바인딩을 사용했는가? | 제6조 |
| 주입 | 셸 명령, eval·exec·Function 등 동적 실행을 제거하거나 승인된 통제로 제한했는가? | 제7조 |
| XSS | innerHTML 등 HTML 직접 삽입을 피하고, 필요한 경우 정화 정책을 적용했는가? | 제8조 |
| 파일 | 업로드 파일의 형식·크기·개수·콘텐츠를 검증하고 **웹 루트 밖**에 저장하는가? | 제9조 |
| 파일 | 다운로드·파일 조회 시 경로 조작 방지와 **객체별 권한 검증**이 이루어지는가? | 제9조 |
| 인증/인가 | 모든 보호 기능과 API에서 **서버 측** 인증·권한 검증을 수행하는가? | 제10조 |
| 세션 | 쿠키 Secure/HttpOnly/SameSite, 세션 재발급·만료·무효화가 적용되었는가? | 제11조 |
| 중요정보 | 비밀번호·키·토큰·개인정보가 소스·설정·로그·오류화면에 노출되지 않는가? | 제12조 |
| 암호화 | TLS 인증서 검증이 활성화되어 있고, 비밀번호에 **적응형 단방향 해시**를 사용하는가? | 제12조 |
| 오류/로그 | 사용자 오류 응답에 스택트레이스·경로·쿼리·민감정보가 노출되지 않는가? | 제13조 |
| 역직렬화 | 신뢰할 수 없는 데이터에 위험한 역직렬화·XML 외부 엔터티 처리를 사용하지 않는가? | 제14조 |
| 외부연동 | 외부 URL 호출에 허용목록·사설망 차단·시간초과·응답 크기 제한이 적용되었는가? | 제15조 |
| 자원 | 요청·페이징·파일·연결에 크기 및 시간 제한, 필요 시 rate limit이 적용되었는가? | 제16조 |
| Python | pickle/unsafe YAML, shell=True, 인증서 검증 비활성화가 없는가? | 제17조 |
| JavaScript | eval/new Function, 위험한 DOM 삽입, shell 호출, 프로토타입 오염 가능성이 없는가? | 제18조 |
| 오픈소스 | 의존성 목록과 잠금 파일이 관리되고 알려진 고위험 취약점이 조치되었는가? | 제6장 |
| 점검 | 코드리뷰·자동화 점검 결과와 **조치 검증 결과**가 보관되었는가? | 제19조 |
| 예외 | 미조치 항목은 위험평가·보완통제·**만료일**을 포함한 승인 기록이 있는가? | 제9장 |
